Domain 1: Secure Architectures · 30%

Security is the biggest slice of the exam. AWS uses a shared responsibility model: AWS secures the cloud (hardware, facilities); you secure what's in it (data, access, config). Master identity, network boundaries, and encryption and you own this domain.

👤IAM — Identity & Access Management▶

IAM is the front door to everything in AWS. For every API call it answers: "Is this principal allowed to do this action on this resource?"

The four building blocks

Users — a person or app, long-term credentials Groups — a bucket of users sharing permissions Roles — temporary identity anything can assume Policies — JSON documents that grant/deny

Permissions come from policies — JSON with Effect (Allow/Deny), Action, Resource, Conditions. An explicit Deny always wins over any Allow.

Roles are the star of the exam

A role has no password — it's a set of permissions an EC2 instance, Lambda, or another account can temporarily "wear." This is how you give EC2 access to S3 without storing keys on it.

🪄 Picture it: a role is a uniform on a hook at work. Nobody owns it — anyone authorized puts it on, gains that job's permissions for a shift, then hangs it back. No permanent keys to leak.

🎯 Key takeaways

  • Grant least privilege — start with nothing, add only what's needed.
  • Use ROLES for EC2/Lambda/services — never hard-code access keys.
  • Explicit Deny beats any Allow; no permission = implicit deny.
  • Use groups to manage permissions at scale, not per-user policies.
🧠 CHECK YOURSELF
An EC2 app needs to read from an S3 bucket. Most secure way to grant access?
  1. Store IAM access keys in the app's config file
  2. Attach an IAM role to the EC2 instance
  3. Make the S3 bucket public
  4. Embed keys in an environment variable
Show answer
B — Attach an IAM role. An instance role provides temporary, auto-rotated credentials via the metadata service — no long-term keys to store, leak, or rotate manually.
🪪Federation, STS & Cross-Account Access▶

Most companies already have identities (corporate directory, Google). Federation lets those users access AWS without separate IAM users for each.

The key players

STS — issues short-lived temporary credentials AssumeRole — the API to "wear" a role IAM Identity Center — SSO for workforce → many accounts Cognito — identity for your app's end users (web/mobile)

Cross-account access

To let Account B use resources in Account A: create a role in A that trusts B, then principals in B call AssumeRole. No shared keys, fully auditable, easily revoked.

🪄 Picture it: federation is a visitor badge. No permanent employee ID — reception verifies you against an external system, prints a badge that expires at end of day. STS is the badge printer.

🎯 Key takeaways

  • Workforce SSO across many accounts → IAM Identity Center.
  • App end-users with Google/Facebook login → Cognito.
  • Cross-account = role in target account with a trust policy + AssumeRole.
  • STS credentials are temporary — they auto-expire, reducing blast radius.
🧠 CHECK YOURSELF
A mobile app needs millions of end users to sign in with Google and get temporary AWS access to upload to S3. Which service?
  1. Amazon Cognito
  2. IAM users for each person
  3. IAM Identity Center
  4. AWS Directory Service
Show answer
A — Amazon Cognito. Purpose-built for customer-facing app identity at scale, supports social/identity-provider login, and brokers temporary AWS credentials. IAM users don't scale to millions of customers.
🧱Network Security — Security Groups vs NACLs▶

Inside a VPC, two firewalls control traffic — and the exam loves the distinction.

AspectSecurity GroupNetwork ACL
Operates atInstance / ENI levelSubnet level
StateStateful — return traffic auto-allowedStateless — allow both directions
RulesAllow onlyAllow and Deny
EvaluationAll rules evaluatedNumber order, first match wins
Use it to…Permit app traffic to instancesBlock a bad IP across a subnet

Because NACLs can explicitly deny, they're your tool for blocking a malicious IP range. Security Groups only allow, so they can't "block" anything specifically.

🪄 Picture it: a Security Group is the bouncer at the club door — checks each guest and remembers you (stateful). A NACL is the guard at the neighborhood gate — checks everyone, keeps a denylist, no memory of who passed (stateless).

🎯 Key takeaways

  • SG = stateful, instance-level, allow-only.
  • NACL = stateless, subnet-level, allow + DENY.
  • Need to block a specific IP? → NACL (it can deny).
  • SGs can reference other SGs — great for tier-to-tier rules.
🧠 CHECK YOURSELF
You must block a single known-malicious IP from reaching any instance in a subnet. What do you use?
  1. A Security Group inbound deny rule
  2. A Network ACL deny rule
  3. An IAM policy
  4. A route table entry
Show answer
B — Network ACL deny rule. Only NACLs support explicit DENY and operate at the subnet level. Security Groups are allow-only, so they can't block a specific IP.
🔑Data Protection — KMS, Encryption & Secrets▶

Protect data at rest (stored) and in transit (over the network).

Encryption at rest → KMS

AWS KMS manages keys. Most services (S3, EBS, RDS) integrate natively — you just pick a key. Keys never leave KMS; services ask KMS to encrypt/decrypt.

SSE-S3 — AWS manages keys, simplest SSE-KMS — you control key + get audit trail ACM — free TLS certs for in-transit (HTTPS) CloudHSM — dedicated hardware, single-tenant

Secrets, not hard-coding

Secrets Manager stores DB passwords/API keys and can auto-rotate them. Parameter Store (SSM) is a cheaper option for config + secrets without auto-rotation.

🪄 Picture it: KMS is a bank vault that never lets keys leave the building. You hand your locked box to a teller (S3/EBS); the vault — not you — does the locking, and you get a log of every open.

🎯 Key takeaways

  • At rest → KMS-integrated encryption (SSE-KMS for control + audit).
  • In transit → TLS/HTTPS, certs from ACM (free, auto-renewing).
  • DB credentials with automatic rotation → Secrets Manager.
  • Single-tenant dedicated hardware / compliance → CloudHSM.
🧠 CHECK YOURSELF
Store an RDS database password and rotate it automatically every 30 days. Which service?
  1. SSM Parameter Store (standard)
  2. AWS Secrets Manager
  3. An encrypted S3 object
  4. KMS key policy
Show answer
B — Secrets Manager. Natively supports automatic credential rotation (with built-in RDS integration). Parameter Store stores secrets but doesn't auto-rotate without custom work.
🛰️Detection, Monitoring & Edge Protection▶

Security isn't just walls — you need to see what's happening and stop attacks at the edge.

Know who did what

CloudTrail — records every API call (who/when) Config — tracks resource config + compliance over time CloudWatch — metrics, logs, alarms

Threat detection trio

GuardDuty — intelligent threat detection from logs Macie — finds sensitive data (PII) in S3 Inspector — scans workloads for vulnerabilities Security Hub — aggregates all findings

Edge protection

WAF filters web requests (SQL injection, bad bots) on ALB/CloudFront/API Gateway. Shield handles DDoS — Standard is free/automatic, Advanced adds cost protection + a response team.

🪄 Picture it: CloudTrail is the building's CCTV on every door. GuardDuty is the analyst who flags "someone's trying every door at 3am." WAF + Shield are the guards at the gate turning away troublemakers.

🎯 Key takeaways

  • Audit trail of API activity → CloudTrail.
  • Detect sensitive data (PII) in S3 → Macie.
  • Intelligent threat detection from logs → GuardDuty.
  • Filter malicious web requests (SQLi/XSS) → WAF; DDoS → Shield.
🧠 CHECK YOURSELF
Auditors ask: "who deleted that S3 bucket and when?" Which service answers this?
  1. Amazon GuardDuty
  2. AWS CloudTrail
  3. Amazon Macie
  4. AWS Config
Show answer
B — CloudTrail. Logs every API call with identity, timestamp, and source IP — the definitive "who did what, when." GuardDuty detects threats; Macie finds sensitive data; Config tracks configuration state.

Domain 2: Resilient Architectures · 26%

Resilience = the system keeps working (or recovers fast) when things break — and things will break. Spread across multiple Availability Zones, decouple components so one failure doesn't cascade, and have a disaster recovery plan sized to your downtime tolerance.

🏢High Availability & Multi-AZ▶

A Region (e.g. us-east-1) contains multiple Availability Zones — physically separate data centers with independent power/network. Golden rule: spread across AZs so losing one doesn't take you down.

The HA toolkit

ELB — spreads traffic across healthy targets in many AZs Auto Scaling Group — replaces failed instances, scales with demand RDS Multi-AZ — synchronous standby in another AZ, auto-failover

ELB + ASG is the classic HA web tier: the load balancer health-checks instances and stops routing to unhealthy ones; the ASG launches replacements across AZs.

Multi-AZ ≠ Read Replica

Multi-AZ = availability (a standby that takes over on failure — you don't read from it). Read Replicas = scaling reads. The exam tests this difference constantly.

🪄 Picture it: Multi-AZ is a backup generator wired to auto-start the instant power flickers — silent until needed. A read replica is extra cashiers for a busy checkout — about load, not surviving an outage.

🎯 Key takeaways

  • Always deploy across ≥2 Availability Zones for HA.
  • ELB + Auto Scaling Group = self-healing, elastic web tier.
  • RDS Multi-AZ = availability/failover (synchronous standby).
  • RDS Read Replica = scale reads (asynchronous, can be cross-region).
🧠 CHECK YOURSELF
A relational DB must survive an AZ outage with automatic failover and no data loss. What do you enable?
  1. A read replica in the same AZ
  2. RDS Multi-AZ deployment
  3. A larger instance type
  4. Daily snapshots only
Show answer
B — RDS Multi-AZ. Maintains a synchronous standby in a second AZ and fails over automatically. Read replicas are asynchronous and meant for scaling reads, not failover.
🔗Decoupling — SQS, SNS & EventBridge▶

Tightly-coupled systems fail together. Decoupling puts a buffer between components so a slow or failed consumer doesn't break the producer.

ServicePatternUse when…
SQSQueue (producer → consumer pool, pull)Buffer work, absorb spikes, async
SNSPub/Sub (1 message → many subscribers, push)Fan-out one event to many systems
EventBridgeEvent bus with filtering rulesRoute by content, SaaS/AWS integrations

The fan-out pattern

Combine them: publish one message to an SNS topic that fans out to multiple SQS queues — each downstream system gets its own durable copy to process at its own pace.

SQS FIFO guarantees ordering + exactly-once; standard SQS is best-effort ordering, at-least-once, higher throughput.

🪄 Picture it: SQS is a restaurant ticket rail — orders queue, cooks grab them when ready; a slammed kitchen doesn't stop ordering. SNS is a PA announcement — say it once, everyone subscribed hears it.

🎯 Key takeaways

  • Buffer/absorb load between tiers → SQS (pull-based queue).
  • Send one event to many subscribers → SNS (push pub/sub).
  • Fan-out durably → SNS topic → multiple SQS queues.
  • Strict ordering + no duplicates → SQS FIFO.
🧠 CHECK YOURSELF
One "order placed" event must trigger billing, inventory AND email — each independent and durable. Best design?
  1. A single SQS queue read by all three
  2. SNS topic fanning out to three SQS queues
  3. Direct synchronous API calls to all three
  4. EventBridge scheduled rule
Show answer
B — SNS fan-out to three SQS queues. Each system gets its own durable copy to process at its own pace — resilient and decoupled. A single shared queue would let only one consumer grab each message.
🌐Disaster Recovery Strategies▶

DR is about two numbers: RTO (how fast you must recover) and RPO (how much data loss you can tolerate). Four strategies trade cost vs speed:

StrategyRecoveryCostHow
Backup & RestoreHours$Restore from backups when disaster hits
Pilot Light10s of min$$Core (DB) always on; scale up rest on demand
Warm StandbyMinutes$$$Scaled-down full copy running; scale up
Multi-Site Active/Active~0$$$$Full prod in 2+ regions serving live traffic

The cheaper the strategy, the longer the recovery. Pick based on what downtime/data loss the business can accept.

🪄 Picture it — spare tire options: Backup & Restore = call a tow truck. Pilot Light = donut spare in the trunk. Warm Standby = full spare mounted and inflated. Multi-Site = a second identical car beside you — instant, but you pay for two.

🎯 Key takeaways

  • RTO = recovery time tolerance; RPO = data-loss tolerance.
  • Lowest cost, highest downtime → Backup & Restore.
  • Near-zero downtime, highest cost → Multi-Site active/active.
  • Pilot Light keeps only the critical core (e.g. DB) warm.
🧠 CHECK YOURSELF
A business tolerates ~10 min downtime and minimizes cost by keeping only the database replicated and running. Which DR strategy?
  1. Backup & Restore
  2. Pilot Light
  3. Multi-Site Active/Active
  4. Warm Standby
Show answer
B — Pilot Light. Keeps the critical core (the database) live and replicated while the rest stays off until needed — a low RTO at lower cost than warm standby or multi-site.
💾Durability, Backups & Route 53 Failover▶

Availability = is it up right now? Durability = will the data still exist later? Don't confuse them.

Durable storage

S3 gives 11 nines (99.999999999%) durability, auto-replicating across AZs. For DR, enable S3 Cross-Region Replication. RDS automated snapshots can be copied cross-region too.

DNS-level failover with Route 53

Route 53 does more than DNS — its health checks + routing policies enable failover:

Failover — primary → secondary if primary unhealthy Latency — send users to the lowest-latency region Weighted — split traffic % (canary/blue-green) Geolocation — route by user location
🪄 Picture it: durability is keeping 11 photocopies in 11 fireproof safes — a few burn, the document survives. Route 53 failover is a receptionist who auto-forwards callers to the backup office when the main line rings out.

🎯 Key takeaways

  • S3 = 11 nines durability, auto-replicated across AZs.
  • Cross-region DR → S3 Cross-Region Replication / copy snapshots.
  • Route 53 Failover routing + health checks = automatic regional failover.
  • Availability ≠ durability — know which the question asks about.
🧠 CHECK YOURSELF
Users should be auto-redirected to a standby region if the primary endpoint fails its health check. Which Route 53 routing policy?
  1. Weighted routing
  2. Failover routing
  3. Simple routing
  4. Multivalue answer
Show answer
B — Failover routing. Pairs a primary and secondary record with health checks, sending traffic to the secondary when the primary is unhealthy.

Domain 3: High-Performing Architectures · 24%

Pick the right tool for the workload so it's fast and scalable. Match compute, storage, database, and delivery to the actual access pattern. When in doubt, prefer managed + elastic options that scale automatically.

🖥️Compute — EC2, Lambda & Containers▶

Pick compute by how much control vs. how little ops you want:

EC2 — full VMs, max control, you manage scaling Lambda — serverless functions, event-driven, scale to zero ECS/EKS — containers; Fargate = serverless containers

EC2 families (letters mean something)

T=burstable/general, M=balanced, C=compute-optimized (CPU-heavy), R=memory-optimized (in-memory/cache), I=storage I/O, P/G=GPU. Match the bottleneck: CPU-bound batch → C; in-memory DB → R.

Scaling automatically

Auto Scaling adds/removes EC2 by metrics. Lambda scales per-request with zero idle cost. For unpredictable spikes with no servers to manage, serverless wins.

🪄 Picture it: EC2 is owning a kitchen — total control, but you staff and maintain it. Lambda is a food truck that appears only when a customer orders, then vanishes — pay per meal, ten trucks appear instantly if ten people order.

🎯 Key takeaways

  • Spiky/event-driven, no servers to manage → Lambda.
  • CPU-heavy → C-family; memory-heavy → R-family.
  • Containers without managing servers → ECS/EKS on Fargate.
  • Steady, full-control workloads → EC2 + Auto Scaling.
🧠 CHECK YOURSELF
An image task runs sporadically, a few seconds per image, with unpredictable bursts. Most cost/perf-efficient compute?
  1. A large always-on EC2 instance
  2. AWS Lambda
  3. A reserved EC2 fleet
  4. EC2 with a fixed Auto Scaling size
Show answer
B — AWS Lambda. Scales instantly per request, runs only during the seconds of work, and costs nothing when idle — ideal for short, sporadic, bursty tasks.
🗄️Storage Performance — EBS, EFS, FSx, S3▶

Choose storage by how it's accessed:

TypeWhatUse when…
EBSBlock storage, one instanceBoot volumes, databases — single-instance disk
EFSShared NFS file system, multi-AZ, LinuxMany Linux instances need the same files
FSxManaged Windows (SMB) / Lustre (HPC)Windows shares; high-perf compute
S3Object storage, internet-scaleFiles, backups, static assets, data lakes
Instance StorePhysically attached, ephemeralTemp scratch/cache (lost on stop)

Key trap: a file system shared by many Linux instances across AZs? That's EFS — not S3 (object storage, not mountable) and not EBS (attaches to one instance).

🪄 Picture it: EBS = the internal drive in one laptop. EFS = a shared network drive the whole office mounts. S3 = a warehouse you fetch boxes from by label. Instance store = a scratchpad wiped at power-off.

🎯 Key takeaways

  • Shared file system, many Linux instances, multi-AZ → EFS.
  • Single-instance block volume (DB, boot) → EBS.
  • Windows file share → FSx for Windows; HPC → FSx for Lustre.
  • Objects/backups/static content at scale → S3.
🧠 CHECK YOURSELF
A fleet of Linux web servers across AZs must read/write the same files concurrently. Which storage?
  1. Amazon S3
  2. Amazon EBS volume
  3. Amazon EFS
  4. EC2 Instance Store
Show answer
C — Amazon EFS. A managed, multi-AZ shared NFS file system many Linux instances can mount at once. EBS attaches to a single instance; S3 isn't a mountable POSIX file system.
🛢️Databases & Caching▶

Match the data model to the database:

RDS — managed relational (MySQL/Postgres…) Aurora — AWS high-perf relational, 5x MySQL DynamoDB — serverless NoSQL, single-digit ms at scale ElastiCache — in-memory cache (Redis/Memcached)

Scaling reads

DB read-heavy and slow? Add Read Replicas (offload reads) or put ElastiCache in front (serve hot data from memory in microseconds, cutting DB load).

When to pick DynamoDB

Massive scale, simple key-based access, unpredictable traffic, single-digit-ms latency, zero server management → DynamoDB. Auto-scales, serverless.

🪄 Picture it: ElastiCache keeps your most-used items on the desk instead of walking to the filing cabinet (the DB) each time. A read replica is photocopying popular files so many people read at once without crowding the original.

🎯 Key takeaways

  • Repeated reads of hot data → ElastiCache (in-memory).
  • Offload read traffic from primary → Read Replicas.
  • Internet-scale NoSQL, ms latency, serverless → DynamoDB.
  • High-performance managed relational → Aurora.
🧠 CHECK YOURSELF
A relational DB is overwhelmed by repeated identical reads of the same popular data. Lowest-latency fix?
  1. Add an ElastiCache caching layer
  2. Switch to a bigger instance monthly
  3. Move to S3
  4. Add more Security Groups
Show answer
A — ElastiCache. Serves frequently-requested data from memory in microseconds, slashing repeated DB load. (Read replicas help too, but caching gives the lowest latency for repeated identical reads.)
🚀Content Delivery & Global Acceleration▶

Get content close to users to cut latency:

CloudFront — CDN, caches content at edge locations Global Accelerator — routes over AWS backbone via anycast IPs Placement Groups — control EC2 placement for network perf

CloudFront vs Global Accelerator

CloudFront = caches HTTP/S content (images, video, web) at edges. Global Accelerator = improves non-HTTP / TCP/UDP apps (gaming, IoT, APIs), gives static anycast IPs — it doesn't cache, it optimizes the network path.

Placement groups

Cluster = pack instances close for low-latency HPC; Spread = separate for resilience; Partition = grouped hardware partitions for big distributed systems.

🪄 Picture it: CloudFront opens local branch stores worldwide stocked with copies of popular products. Global Accelerator is a private express highway to HQ — stocks nothing locally, just makes the trip faster.

🎯 Key takeaways

  • Cache static/dynamic web content near users → CloudFront.
  • Speed up TCP/UDP or non-cacheable apps globally → Global Accelerator.
  • Static anycast entry IPs + fast failover → Global Accelerator.
  • Low-latency between instances (HPC) → Cluster placement group.
🧠 CHECK YOURSELF
A global video site wants lower latency and to offload origin servers by caching media near viewers. Which service?
  1. AWS Global Accelerator
  2. Amazon CloudFront
  3. A larger EC2 instance
  4. AWS Direct Connect
Show answer
B — CloudFront. A CDN that caches content at edge locations near viewers, cutting latency and offloading the origin. Global Accelerator optimizes network paths but doesn't cache.

Domain 4: Cost-Optimized Architectures · 20%

Same result, lowest bill. Match pricing models to usage, pick the right storage tier for access frequency, turn off what you don't need, and watch spend with the right tools. Smallest domain, but easy points once you know the levers.

🏷️EC2 Pricing Models▶

Four ways to pay for EC2 — choosing right can cut costs 70%+:

ModelSavingsUse when…
On-DemandBaselineShort-term, unpredictable, can't be interrupted
Savings Plans / ReservedUp to ~72%Steady, predictable usage (1 or 3-yr commit)
SpotUp to ~90%Fault-tolerant, flexible, interruption-OK work
Dedicated HostsPremiumLicensing/compliance needing physical isolation

The Spot rule

Spot = spare capacity at huge discount, but AWS can reclaim it with 2 min notice. Great for fault-tolerant batch, big-data, CI. Never for stateful, must-stay-up workloads. Savings Plans = the flexible commitment for steady baseline compute.

🪄 Picture it: On-Demand = a hotel booked nightly (flexible, priciest). Savings Plan = a 1-year lease (commit, pay much less). Spot = standby airline tickets — dirt cheap but you can get bumped, so only fly when flexible.

🎯 Key takeaways

  • Steady, predictable baseline → Savings Plans / Reserved.
  • Fault-tolerant, interruptible batch → Spot (up to ~90% off).
  • Short, unpredictable, can't-be-interrupted → On-Demand.
  • Never run stateful must-stay-up systems on Spot.
🧠 CHECK YOURSELF
A nightly batch job can be safely interrupted and restarted, and you want the lowest compute cost. Which pricing model?
  1. On-Demand Instances
  2. Spot Instances
  3. Dedicated Hosts
  4. Reserved Instances
Show answer
B — Spot Instances. Deepest discount (up to ~90%) and ideal for fault-tolerant, interruption-tolerant work like restartable batch. On-Demand and Reserved cost far more for this flexible workload.
🪣S3 Storage Classes & Lifecycle▶

Pay less by matching storage class to access frequency:

ClassBest for
S3 StandardFrequently accessed, hot data
Intelligent-TieringUnknown/changing access — auto-moves tiers
Standard-IA / One Zone-IAInfrequent access (lower storage, retrieval fee)
Glacier Instant/Flexible/Deep ArchiveArchive — cheapest, retrieval delay (mins→hours)

Two big exam levers

Lifecycle policies auto-transition objects to cheaper tiers (or delete) as they age — e.g. logs: Standard → IA at 30d → Glacier at 90d → delete at 7y. Intelligent-Tiering is the answer when access is unknown/unpredictable — it auto-optimizes with no retrieval penalties.

🪄 Picture it: daily stuff on the shelf (Standard), seasonal items in the closet (IA), heirlooms in a distant storage unit (Glacier). Intelligent-Tiering is a smart assistant who moves things between them based on what you actually touch.

🎯 Key takeaways

  • Unknown/changing access patterns → S3 Intelligent-Tiering.
  • Automate tier transitions by age → S3 Lifecycle policies.
  • Rarely accessed but needs fast retrieval → Standard-IA.
  • Long-term archive, cheapest → Glacier Deep Archive.

  1. S3 Glacier Deep Archive
  2. S3 Standard
  3. S3 Intelligent-Tiering
  4. S3 One Zone-IA
Show answer

⏰Right-Sizing, Scheduling & Serverless Savings▶

The cheapest resource is the one you're not running.

Stop paying for idle

Right-sizing: match instance size to real utilization (Compute Optimizer recommends). Scheduling: stop/start non-prod instances outside business hours — a dev fleet running 24/7 wastes ~65% of its cost.

Scheduling vs Spot

For stateful dev/test instances that must keep their data, the win is stop/start scheduling — NOT Spot (Spot terminates them and loses state). Spot is only for interruption-tolerant work.

Go serverless

Lambda, Fargate, DynamoDB on-demand, Aurora Serverless scale to zero — pay nothing when idle, eliminating waste for spiky workloads.

🪄 Picture it: leaving dev servers on overnight is like leaving every light and the AC running in an empty office all weekend. Scheduling is the timer that shuts it off at 6pm and back on at 8am — same productivity, a fraction of the bill.

🎯 Key takeaways

  • Stateful dev/test fleet → stop/start scheduling (keeps data).
  • Match size to real usage → right-sizing (Compute Optimizer).
  • Spiky/idle workloads → serverless scales to zero.
  • Don't use Spot for instances that must preserve state.
🧠 CHECK YOURSELF
Stateful dev EC2 instances are used 9am–6pm weekdays but run 24/7. Best cost optimization?
  1. Move them to Spot Instances
  2. Schedule automatic stop/start outside business hours
  3. Buy 3-year Reserved Instances
  4. Switch to the largest instance type
Show answer
B — Stop/start scheduling. Cuts the bill for predictable usage hours while preserving state. Spot would terminate them and lose data; Reserved suits always-on steady usage.

Cut transfer costs

Transfer out to the internet costs money; into AWS is usually free. A NAT Gateway charges per hour + per GB — route S3/DynamoDB traffic through a free VPC Gateway Endpoint instead.

  1. AWS Cost Explorer
  2. AWS Budgets
  3. AWS Trusted Advisor
  4. Cost Allocation Tags
Show answer
B — AWS Budgets. Set cost/usage thresholds and get alerts when actual or forecasted spend crosses them. Cost Explorer analyzes spend but doesn't send threshold alerts.
